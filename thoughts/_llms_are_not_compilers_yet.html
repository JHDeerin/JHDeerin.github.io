AI is Not A Spec-to-Source Code Compiler (Yet)

There's been a take going around recently that I've heard a few times by now (should cite sources, like the Simon Willison "vibe coding vs agentic engineering" post https://simonwillison.net/2026/May/6/vibe-coding-and-agentic-engineering/, or his dark factory post https://simonwillison.net/2026/Feb/7/software-factory/, or whatever Brian read): AI (the LLM kind) is like a compiler. A compiler takes in source code and spits out assembly code, or a binary, or some other thing that runs on a computer, and most programmers have no idea how it works. And that's fine. You trust the compiler output and move on with your day. Unless you're doing something very special or have won the bugapalooza, you can go a whole programming career without knowing the details of how your Javascript gets interpreted or how your C++ code turns into an executable, and still be very productive. If there's a bug, it's not the compiler's fault - it's your code's fault. You just need to fix your code (left as a variable-difficulty exercise for the reader) - you don't need to look at the compiled stuff at all. AI - the take goes - should be treated as a compiler for your thoughts. It takes in your thoughts - let's say some well-organized thoughts written down in a specification - and converts them into source code that your computer can run. You don't understand the source code any more than you understand the assembly spat out by a traditional compiler - and that's fine. You can run it. You can try out the output program itself, and if there's an issue, you fix your input spec. Call it "vibe coding" if you like, but fundamentally it's the same idea - the source code doesn't have to be understood. You treat the AI as a compiler and don't worry about the source code, and unless you're doing something really specialized that's perfectly fine. In fact, it's what you should do; worrying about the source code is just needlessly slowing you down, a bad habit from a bygone era when the computer couldn't do this stuff for us. When I hear this take, I get the same vague sinking feeling in my head as if a friend had just told me he'd received a wonderful business opportunity from a Burundian prince. Perhaps he really did get a great deal. Perhaps. But I don't buy it. (There is an equal and opposite take I've seen for even longer: insert "code. you just described code" comic - although that might be better for a footnote, since my point isn't so much about the spec basically being code here, as it is about how even if the spec were code-equivalent, LLMs still ain't as good as compilers) (feel like Marc Brooker has a post about iterating on specs in agentic engineering that I should re-read for this - yup, two relevant ones: - https://brooker.co.za/blog/2025/12/16/natural-language.html - https://brooker.co.za/blog/2026/04/09/waterfall-vs-spec.html) There are a few reasons I'm skeptical about this take. I'll split them into "reasons I don't think you can get away with this right now", and "essential reasons this might not ever work." Why it won't work right now 1. Even with a perfect spec, LLM output is non-deterministic (and not reliable) - Technically, some compilers aren't practically deterministic either - but the variability from run to run is wayyyyyy larger for LLMs. And far, far less reliable. This is a major difference from compilers; if I run my code through different well-regarded compilers at different times, I might get some different binaries that differ in size and performance by some single-digit percentage, or that only support a particular chipset. If I put my spec through 2 different well-regarded LLMs at different times - or, heck, the SAME model at different times - there's a single-digit percent of the time it completely ignores one of the features I told it to build. An LLM deleting a production database when it's explicitly told "never delete a production database" is rare - but how rare? 1 time in 1,000? In 500? In 200? I'd believe any of those numbers - that's way too often for comfort. How often am I worried about a compiler going rogue and completely "forgetting" to build a file? Quite literally never. A compiler error on a normal computer is literally a 1 run in a billion issue - 6 or 7 orders of magnitude less often than LLM prompts. Rare enough a team of 1,000 engineers at a company can each build several dozen times a day and never have any issues for a decade. - Problem is made worse because most major models right now are cloud-based and retired regularly, with no way to use them if a provider pulls them offline. Different LLM models give significantly different output for the same prompt; that's a big problem for reproduceability. 2. Current LLMs are not smart enough to clean up their own filth - This is my bigger issue - LLMs are not able to keep the code in a maintainable state on their own. - While the model I have by far the most experience with is Sonnet 4.6 (not the latest and greatest), I have used Opus 4.7 and GPT-5.4 - and even with them, they seem to have worse architectural sense than most experienced engineers. Sonnet 4.6 has a strong tendency to make new functions and classes instead of reusing what's already there. It will subtly stray away from existing architectural patterns in the code, introducing new, competing ones. LLMs will not refactor on their own; if you tell them to refactor, the same problems tend to emerge if you give them enough freedom (which, paradoxically, is where all the benefits of LLMs come from, them "figuring out" how to do stuff you didn't tell them). And what happens over time is that they make the code base increasingly messy and confusing - not just for the humans, but for themselves. And once it's messy and confusing enough, they won't make changes correctly. They'll update one function but not the other 3 it made that do the same related thing in different parts of the codebase. Bugs will begin mysteriously appearing. A wise human engineer would start "paying off tech debt" at this point, cleaning up the code; the AI will not, and cannot effectively, on its own. At this point, a human might notice the issue and want to refactor - but not having written or read the code themselves, they're much less able to do so vs the old days. 3. Memory limits on LLMs mean that for medium to large codebases, the LLM literally cannot understand the entire thing (and isn't smart enough to pull out abstractions). These are all problems I think are technically solvable. Deterministic models are possible, and models will continue to get smarter with larger context windows. But they are problems today, and there are other, more fundamental concerns I have with the compiler analogy for AI. Essential reasons (noting the Wernher von Braun quote that "I have learned to use the word impossible with great caution" - someone may find a way to solve these someday in a way I can't think of. And maybe Dan Luu's point that Fred Brooks probably significantly underestimated how much software engineering is dealing with "accidental" complexity, not irreducible complexity) 1. By definition, source code is at a higher level of abstraction than assembly code - the goal of source code has always been to specify what you want, not how to do it, and no more. For large classes of programs, what you think of as "internal details" of the code - whether you use a queue or a tree to store stuff, etc. - are actually functional details. LLMs save you time by filling in the gaps and thinking through the stuff you don't know or don't care about - but they are not mind readers, and will sometimes fill in those gaps with wrong guesses. You will not get the spec right the first time, because (as the core, long-suffering and much-abused idea of Agile hopefully taught us) we don't know what we want until we see something working and realize what's missing, and iterate on it. Specs can certainly be iterated on, but what we thought were implementation details may actually be important things that affect observable behavior... - I need to think on this more and develop it, but basically my concern here is that the mental gap between what the "compiler" is filling in between your input and its output is MUCH bigger between "my thoughts -> source code" than between "source code -> assembly". The assumptions that a traditional compiler makes about what you wanted are smaller in scope and matter a lot less; it doesn't affect the functional behavior of the code at a level that matters (user-visible), only how it talks to the computer, which basically only ends up observable as how long things take to run. Source code puts a pretty tight bound on the behavior you want. But a spec to source code, there's a lot more wiggle room. The gap is much bigger. Arguably if you perfectly specify (or over-specify) every observable behavior you want and nothing more, then that'd be a similar situation - you get what you want, and the implementation details would rear their heads in "non-functional requirements" like speed or reliability. - It boils down to conciseness in writing - saying exactly what you mean, everything you meant, and nothing more. Which is notoriously hard. - The ambiguity of natural language also rears its head - once you're writing what you want formally enough to eliminate that ambiguity, you are writing code. 2. Gaps in the spec - unlike a compiler, the LLM will NOT reliably spot critical mistakes in your spec and warn you about them. (Admittedly there are probably even more things compilers can't catch either, e.g. architecture mistakes). But regardless, your spec may have mistakes - who watches the watchman? This isn't necessarily an argument against "AI as compilers", but a cautionary note on the limitation of any such compiler - it's only as good as what you give it. You still have to make sure what you tell it to make is good. 3. Verification - automated tests are important for productivity, but they have to be written, too. Offloading testing to the LLM means either it repeating the spec (and so not testing the important things you forgot to specify), or the AI guessing what you meant and making up the tests - which might not do what you want, and with current LLMs might not even match the spec you give or be coherent. 4. Programs that need to operate at multiple levels of abstraction - a single spec isn't enough for complex programs. You want your regular users to have 1 view, but admins to have a backdoor with extra stuff, and API users to have yet another doorway into the code with a different level of detail, and logs and crash dumps and metrics for L4 support debugging when something goes wrong at still another level. AI as compiler doesn't eliminate this; what it attempts to eliminate is having specify the "internal details" that only a computer needs to worry about. But those details often go deeper than we expect. This is again less of an argument that AI as compiler can't work, as it's pointing out a limitation - it might save us less work than we expect, because we have to care about more behavior than we expect. - Relatedly, Hyrum's law - if the change has any effect on observable behavior whatsoever (which at some point means practically any code change), then someone somewhere will care about it. Traditional compilers have this issue too, but again, from point #1 (source code to assembly is a smaller gap), the size of "undefined behaviors" that we might later end up depending on is smaller. Why this might not matter - Prototypes and scripts, where exact adherence to what you want isn't important AND where long-term maintenance/coherence isn't essential - The smaller and more routine the code, the less the spec matters. If I'm creating something truly custom, I need to specify that carefully - but if I just need a generic in-memory key-value store, that's a well understood concept. If I need a web server to host some static HTML files, at this point LLMs are probably reliable at coding it up, since it's a common concept with plenty of examples. Making an extension for your company's custom in-house framework? That's when I start to trust the default LLM output less. I don't trust LLMs to architect my custom dream house, but I'll trust them a lot more to manufacture the bricks and furniture. - LLMs for creating initial code that you then refine - in this case, the AI isn't treated like a compiler, and the source code isn't treated as an intermediate artifact. Instead, the AI is treated as a tool for making rough drafts, and the code is still reviewed and edited by a human. IMO this is still the most effective way to work with AI coding agents. - In theory, some sort of declarative language that lets you specify just the external behavior/interfaces you care about and then have well-defined "black box" areas you want the AI to fill in - that might be a workable sweet spot. And an interesting idea to explore. "Domain languages" as a concept feels pretty related here - the ability to define a specific language for the problem you're working on that lets you work in terms of concepts you're comfortable with. BDD frameworks like Gherkin, too - perhaps as a cautionary tale (since many people ended up disliking them). I'm not experienced with either enough to know how much ground I'm retreading. - Willison has an analogy that I think I like more: AI-generated software as code that another team wrote. We're not in control of that code and don't plan it, but we can still effectively use and trust code that another team sent us without reading it all ourselves. Why? Because if they're professionals, we trust they've done a high-quality job and their stuff works, and they did the work to understand what we needed - which may well involve iteration and us checking the parts that WE care about do what we want, and trusting the rest is sensibly designed. We already work like this with people, so with a good enough LLM we could work like this, too. The issue is that LLMs today (and frankly many humans) aren't smart enough to do more than what we asked for - to ask good questions and discover the "unknown unknowns" and hidden requirements and gotchas that we didn't even think of because we need to interface with some other system. - The disease might also be part of the cure - LLMs also make explaining and understanding a codebase easier, so that periodic human-guided refactorings might still be possible. People regularly use LLMs to search through a codebase to understand some legacy or forgotten feature. This could be some evidence that the "LLMs mess the code up long-term" argument has less to do with the raw model capabilities, and more to do with their default behavior (e.g. that one blog post about how LLMs tend to default to over-editing, but simple prompt tweaks can partially mitigate it). - I might be attacking a straw man - no one (okay, a few people) is trying to write a perfect spec that will reproduce the same program every time, they're giving the AI a broad prompt, maybe having it construct a PLAN.md file based on that, tweaking it, and then seeing what it gives them and checking if it's good enough to use (and iterating if not). What's wrong with that? Not necessarily anything, but I think there's a temptation to say "eh, the agent built it this way, I'll leave it" and end up with something subpar
